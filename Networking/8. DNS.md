<h2>1. DNS Basics</h2>

<p>
<strong>DNS = Domain Name System</strong>
</p>

<p>
DNS converts a <strong>domain name</strong> into an IP address so that computers
can communicate with the correct server.
</p>

<pre>
google.com → IP Address
</pre>

<p>
<strong>Simple meaning:</strong> DNS = Name → IP Address
</p>

<hr>

<h2>2. DNS Resolution</h2>

<p>
<strong>DNS Resolution</strong> is the process of finding the IP address
associated with a domain name.
</p>

<p>
For example, when you enter:
</p>

<pre>
www.example.com
</pre>

<p>
your system needs to find its IP address before connecting to the server.
</p>

<p>
<strong>DNS Resolution = Finding the IP address for a domain name.</strong>
</p>

<hr>
<h2>3. DNS Resolution Flow — How DNS Finds an IP</h2>
<p>
When a client needs the IP address of a domain, DNS resolution generally
happens through a recursive DNS resolver.
</p>
<h3>Step 1 — Client Request</h3>
<p>
The client asks for the IP address of:
<code>www.example.com</code>
</p>

<h3>Step 2 — Local Cache</h3>

<p>
The system checks whether the DNS answer already exists in its local cache.
If it exists and is still valid, the cached answer can be used.
</p>

<h3>Step 3 — Recursive DNS Resolver</h3>

<p>
If the answer is not available locally, the request is sent to a
<strong>recursive DNS resolver</strong>.
</p>

<h3>Step 4 — Root DNS Server</h3>

<p>
The resolver can query a root DNS server to find where the
<code>.com</code> TLD information is available.
</p>

<h3>Step 5 — TLD DNS Server</h3>

<p>
The <code>.com</code> TLD server points the resolver toward the
<strong>authoritative DNS server</strong> for <code>example.com</code>.
</p>

<h3>Step 6 — Authoritative DNS Server</h3>

<p>
The authoritative DNS server provides the actual DNS record containing
the requested IP address.
</p>

<h3>Step 7 — Response</h3>

<p>
The recursive resolver returns the IP address to the client.
The client can then connect to the destination IP.
</p>

<p>
<strong>Important:</strong> The client normally does not directly query
Root → TLD → Authoritative servers.
The <strong>recursive resolver</strong> performs this lookup on behalf
of the client.
</p>

<hr>

<h2>4. Domain Names &amp; IP Addresses</h2>

<p>
A <strong>domain name</strong> is a human-readable name, while an
<strong>IP address</strong> identifies the network destination.
</p>

<pre>
Domain:
example.com

IP:
93.184.216.34
</pre>

<p>
Multiple domain names can sometimes point to the same IP address, and
a single domain can have multiple IP addresses.
</p>

<hr>

<h2>5. DNS Records</h2>

<p>
DNS records are pieces of information stored in DNS that tell systems
how a domain should be handled.
</p>

<p>Important DNS record types include:</p>

<ul>
  <li>A</li>
  <li>AAAA</li>
  <li>CNAME</li>
  <li>MX</li>
  <li>TXT</li>
  <li>NS</li>
  <li>PTR</li>
</ul>

<hr>

<h2>6. A / AAAA Records</h2>

<h3>A Record</h3>

<p>
An <strong>A record</strong> maps a domain name to an
<strong>IPv4 address</strong>.
</p>

<pre>
example.com → 192.168.1.10
</pre>

<h3>AAAA Record</h3>

<p>
An <strong>AAAA record</strong> maps a domain name to an
<strong>IPv6 address</strong>.
</p>

<pre>
example.com → 2001:db8::10
</pre>

<p>
<strong>A → IPv4</strong><br>
<strong>AAAA → IPv6</strong>
</p>

<hr>

<h2>7. CNAME</h2>

<p>
<strong>CNAME = Canonical Name</strong>
</p>

<p>
A CNAME creates an alias from one hostname to another hostname.
</p>

<pre>
www.example.com
        ↓
example.com
</pre>

<p>
<strong>Simple meaning:</strong>
CNAME = One hostname is an alias for another hostname.
</p>

<hr>

<h2>8. MX</h2>

<p>
<strong>MX = Mail Exchange</strong>
</p>

<p>
MX records specify which mail servers handle email for a domain.
</p>

<pre>
example.com
     ↓
Mail Server
</pre>

<p>
When someone sends email to:
</p>

<pre>
user@example.com
</pre>

<p>
the sending mail system uses the domain's MX records to determine
where the email should be delivered.
</p>

<p>
<strong>SOC Relevance:</strong>
MX records can help during investigations involving suspicious or
phishing-related domains.
</p>

<hr>

<h2>9. TXT</h2>

<p>
<strong>TXT records</strong> store text information associated with a domain.
</p>

<p>Common uses include:</p>

<ul>
  <li>Domain verification</li>
  <li>SPF</li>
  <li>Email security policies</li>
  <li>Administrative information</li>
</ul>

<pre>
example.com → TXT → "verification=..."
</pre>

<p>
<strong>SOC Relevance:</strong>
TXT records can be useful when investigating domains and email-security
configurations.
</p>

<hr>

<h2>10. NS</h2>

<p>
<strong>NS = Name Server</strong>
</p>

<p>
NS records identify the <strong>authoritative DNS servers</strong>
responsible for a domain.
</p>

<pre>
example.com
     ↓
ns1.example-dns.com
ns2.example-dns.com
</pre>

<p>
<strong>Simple meaning:</strong>
NS = Which DNS servers are responsible for this domain?
</p>

<hr>

<h2>11. Recursive DNS</h2>

<p>
A <strong>recursive DNS resolver</strong> receives a DNS request from
a client and finds the answer on the client's behalf.
</p>

<p>
If the answer is not already cached, the resolver can query other
DNS servers to find the required information.
</p>

<p>
<strong>Simple meaning:</strong>
Recursive DNS = Finds the answer for the client.
</p>

<hr>

<h2>12. Authoritative DNS</h2>

<p>
An <strong>authoritative DNS server</strong> contains the official DNS
records for a domain.
</p>

<p>
For example:
</p>

<pre>
example.com → 93.184.216.34
</pre>

<p>
The authoritative DNS server is responsible for providing the official
DNS information for that domain.
</p>

<p>
<strong>Recursive DNS → Finds the answer</strong><br>
<strong>Authoritative DNS → Provides the official answer</strong>
</p>

<hr>

<h2>13. DNS Cache</h2>

<p>
A <strong>DNS cache</strong> stores previously received DNS answers temporarily.
</p>

<pre>
example.com → 93.184.216.34
</pre>

<p>
If the same domain is requested again while the cached record is still valid,
the cached answer may be used instead of performing another full lookup.
</p>

<p><strong>Benefits:</strong></p>

<ul>
  <li>Faster DNS resolution</li>
  <li>Less DNS traffic</li>
  <li>Less work for DNS servers</li>
</ul>

<hr>

<h2>14. Hosts File</h2>

<p>
The <strong>hosts file</strong> is a local file that can manually map
hostnames to IP addresses.
</p>

<pre>
192.168.1.10    server.local
</pre>

<h3>Windows</h3>

<pre>
C:\Windows\System32\drivers\etc\hosts
</pre>

<h3>Linux</h3>

<pre>
/etc/hosts
</pre>

<p>
<strong>SOC Relevance:</strong>
Attackers or malware can sometimes modify the hosts file to redirect users
to a malicious or incorrect IP address.
</p>

<hr>

<h2>15. Reverse DNS</h2>

<p>
Normal DNS resolves:
</p>

<pre>
Domain → IP
</pre>

<p>
<strong>Reverse DNS</strong> does the opposite:
</p>

<pre>
IP → Domain / Hostname
</pre>

<p>
For example:
</p>

<pre>
192.168.1.10 → server.example.com
</pre>

<p>
Reverse DNS commonly uses <strong>PTR records</strong>.
</p>

<p>
<strong>Simple meaning:</strong>
Reverse DNS = Finding the hostname associated with an IP address.
</p>

<hr>

<h2>16. Internal &amp; External DNS</h2>

<h3>Internal DNS</h3>

<p>
Internal DNS is used inside an organization's network.
</p>

<p>It may resolve internal systems such as:</p>

<pre>
fileserver.company.local
printer.company.local
dc01.company.local
</pre>

<p>
These names may not be publicly accessible.
</p>

<h3>External DNS</h3>

<p>
External DNS handles domains that are accessible through the public Internet.
</p>

<pre>
www.company.com
mail.company.com
</pre>

<p>
<strong>Internal DNS → Internal/private resources</strong><br>
<strong>External DNS → Public Internet resources</strong>
</p>

<h2>SOC L1 Connection</h2>

<p>
DNS is extremely useful during security monitoring.
When analyzing DNS activity, pay attention to:
</p>

<ul>
  <li>Which host made the query</li>
  <li>Which domain was queried</li>
  <li>What IP address the domain resolved to</li>
  <li>When the query occurred</li>
  <li>How frequently the domain was queried</li>
</ul>

<p>
Suspicious DNS activity can help identify:
</p>

<ul>
  <li>Malware communication</li>
  <li>Phishing domains</li>
  <li>Command-and-control activity</li>
  <li>DNS tunneling</li>
  <li>Unusual or randomly generated domains</li>
</ul>

<h3>Example</h3>

<pre>
Internal Host
     ↓
DNS Query
     ↓
suspicious-domain.com
     ↓
IP Address
</pre>

<p>
Understanding <strong>Who queried → What domain → What IP → When → How often</strong>
is an important part of DNS analysis for a SOC L1 analyst.
</p>
